# Scenario
A company has a food delivery application that uses Lambda, SQS, and DynamoDB. Orders are initially placed in an SQS queue, then processed by a Lambda function with reserved concurrency. The processed orders are saved into a DynamoDB table with Auto Scaling enabled for read and write capacity. The company is receiving feedback from customers saying that they're facing a delay issue in displaying the order status from their order history page.

# Question
How can the issue be possibly identified and fixed?

# Options
1. Go to the CloudWatch Logs to check for the NumberOfMessagesSent SQS metric and WriteThrottleEvents DynamoDB metric. Increase the SQS visibility timeout and the DynamoDB table's maximum write capacity units.
2. Go to the CloudWatch Logs to check for the ApproximateAgeOfOldestMessage SQS metric and WriteThrottleEvents DynamoDB metric. Increase the reserved concurrency of the Lambda function and the maximum write capacity units of the DynamoDB table.
3. Go to the CloudWatch Logs to check for the ApproximateAgeOfOldestMessage SQS metric and WriteThrottleEvents DynamoDB metric. Increase the Lambda function's execution timeout and the maximum write capacity units of the DynamoDB table.
4. Go to the CloudWatch Logs to check for the Throttles SQS metric and WriteThrottleEvents DynamoDB metric. Set a redrive policy on the SQS queue and increase the DynamoDB table's maximum write capacity units.

# Explanation
Reserved concurrency creates a pool of requests that can only be used by its function, and also prevents its function from using unreserved concurrency.

The ApproximateAgeOfOldestMessage measures the number of seconds since the creation of the oldest message in the queue. This SQS metric is effective because if it goes up, it means that messages are not being processed quickly enough. It can also show you the messages that your consumers can't handle and are stuck in your queue.

WriteThrottleEvents are requests to DynamoDB that exceed the provisioned write capacity units for a table or a GSI.

In this scenario, the ApproximateAgeOfOldestMessage and the WriteThrottleEvents metrics will give you insight into which requests (orders) are experiencing delays. The ApproximateAgeOfOldestMessage metric can give you an idea that the reserved concurrency of the Lambda function is not enough to handle the volume of the orders which causes the delay. Another possible fix is to increase the write capacity of the DynamoDB table. If the orders are not saved to the database then processed orders won't show up to the application. You can check the WriteThrottleEvents metrics in DynamoDB and see if there are requests being throttled. If you've confirmed that the allotted write capacity isn't enough then you can allocate a higher write capacity.

1. The visibility timeout just prevents consumers (Lambda) from processing the same order within a given period of time. This will not help in resolving the delay.
3. The Lambda function's execution timeout limit just defines how long a Lambda function can process an order before it stops running. This won't likely solve the issue. Based on the scenario, the issue is just about a delay and not a failed order — it means that the orders are processed successfully at the Lambda function but the processed orders are somewhat being impeded when they're written to the DynamoDB table level.
4. The redrive policy just specifies how failed messages from a source queue are moved to a dead letter queue. This won't really solve the issue.
