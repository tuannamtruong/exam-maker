# Scenario
A new system should be configured for security purposes to detect suspicious activities in any of its accounts, such as SSH brute force attacks or compromised EC2 instances that serve malware. All gathered information must be centrally stored in its dedicated security account for audit purposes, and the events should be stored in an S3 bucket.

# Question
Which solution?

# Options
1. Automatically detect SSH brute force or malware attacks by only enabling GuardDuty in the security account. Set up the security account as the GuardDuty Administrator for every member account. Create a new EventBridge rule in the security account. Configure the rule to send all findings to Kinesis Data Streams. Launch a custom shell script in the Lambda function to read data from the Kinesis Data Streams and push it to the S3 bucket.
2. Automatically detect SSH brute force or malware attacks by enabling GuardDuty in every account. Configure the security account as the GuardDuty Administrator for all member accounts in the organization. Set up a new EventBridge rule in the security account. Configure the rule to send all findings to Data Firehose, pushing the findings to the S3 bucket.

# Explanation
GuardDuty enables and manages across multiple accounts efficiently. All member account findings can be aggregated through the multi-account feature with a GuardDuty administrator account. This allows the security team to manage all GuardDuty findings across the organization in one account. The aggregated findings are also available through EventBridge, making integration with an existing enterprise event management system easy.

1. Although using GuardDuty in this scenario is valid, the implementation for storing the findings is incorrect. You can typically configure the EventBridge rule to send all findings to Data Firehose, pushing the findings to the S3 bucket.
