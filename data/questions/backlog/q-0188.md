# Scenario
AnyCompany manages multiple AWS accounts by using Organizations.

Existing member accounts are accessed through an IAM role named OrganizationAccountAccessRole.
Example Corp's existing AWS account joined the organization through an Organizations invitation.
The DevOps engineer cannot assume OrganizationAccountAccessRole in the new member account.

# Options
1. In the management account, grant the DevOps engineer's IAM user permission to assume the OrganizationAccountAccessRole IAM role in the new member account.
2. In the management account, create a new SCP. In the SCP, grant the DevOps engineer's IAM user full access to all resources in the new member account. Attach the SCP to the OU that contains the new member account.
3. In the new member account, create a new IAM role that is named OrganizationAccountAccessRole. Attach the AdministratorAccess AWS managed policy to the role. In the role's trust policy, grant the management account permission to assume the role.
4. In the new member account, edit the trust policy for the OrganizationAccountAccessRole IAM role. Grant the management account permission to assume the role.

# Explanation
Cross-account role assumption requires both: the caller has permission to call sts:AssumeRole, and the target role trusts the caller.

1. The DevOps engineer already has permission to call sts:AssumeRole through their existing setup.
2. SCPs never grant permissions.
3. This would work only if the role does not already exist. Creating another role with the same name is impossible.
