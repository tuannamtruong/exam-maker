# Scenario
You have migrated your application API server from a cluster of EC2 instances to a combination of API gateway and AWS Lambda. You are used to canary deployments on your EC2 cluster where you carefully check any errors on the application before doing the full deployment. However, you can't do this on your current AWS Lambda setup since the deployment switches quickly from one version to another.

# Question
How can you implement the same functionality on AWS Lambda?

# Options
1. Use Route 53 weighted routing policy with API Gateway.
2. Deploy your app using Traffic shifting with AWS Lambda aliases.
3. Use CodeDeploy to perform rolling update of the latest Lambda function.
4. Deploy your app using Traffic shifting with Route 53.

# Explanation
By default, an alias points to a single Lambda function version. You can implement the routing-config parameter of the Lambda alias that allows you to point to two different versions of the Lambda function and dictate what percentage of incoming traffic is sent to each version.

1. Although technically valid, this is not an efficient solution to perform canary deployments of Lambda functions. Traffic splitting uses an alias to switch between two functions in the backend allowing you to maintain a single instance of API Gateway + Lambda function. With weighted routing, you need to deploy the new version on a new instance of API Gateway + Lambda.
3. AWS Lambda does not support native rolling update. Deployments of a Lambda function could only be performed in a single flip by updating the function code for version $LATEST, or by updating an alias to target a different function version.
4. Route 53 does not support traffic shifting for Lambda deployments.
