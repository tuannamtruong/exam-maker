# Scenario
The portal is hosted in an ASG of On-Demand EC2 instances across three multiple Availability Zones. New requirement to improve the system monitoring of the application as well to track the number of payment and refund transactions being done every minute. The DevOps team should also be notified if this metric breaches the specified threshold.

# Question
Which of the following options provides the MOST cost-effective and automated solution that will satisfy the above requirement?

# Options
1. Set up an ELK Stack in AWS using OpenSearch service for log processing. Store the payments and refund transactions in each instance and configure Logstash to send the logs to OpenSearch. Set up a Kibana dashboard to view the data and the metric graphs.
2. Configure the instances to push the number of payments and refund transactions to CloudWatch Logs as a custom metric. Develop a custom monitoring application using a Python-based Flask web application to view the metrics and host it in an EC2 instance.
3. Configure the instances to push the number of payments and refund transactions to CloudWatch as a custom metric. Set up a CloudWatch alarm to notify the DevOps team using SNS when the threshold is breached. View statistical graphs of your published metrics with the Management Console.
4. Configure the instances to push the entire log of each payment and refund transactions to EventBridge as a custom metric. Set up a CloudWatch alarm to notify the DevOps team using SNS when the threshold is breached. View statistical graphs of your published metrics with the Management Console.

# Explanation
Metric data is kept for 15 months, enabling you to view both up-to-the-minute data and historical data. You can publish your own metrics to CloudWatch using the CLI or an API. You can view statistical graphs of your published metrics with the Management Console.

CloudWatch stores data about a metric as a series of data points. Each data point has an associated timestamp. You can even publish an aggregated set of data points called a statistic set. You can aggregate your data before you publish it to CloudWatch.

1. Although this solution may work, it entails a lot of effort to set up and costs more to maintain. A more cost-effective solution is to primarily use custom metrics in CloudWatch.
2. it will typically take you a considerable amount of time to set up the Flask web app. Running this solution also entails an added monthly cost.
4. you can't push a custom metric using EventBridge.
