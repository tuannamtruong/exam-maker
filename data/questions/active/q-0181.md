correct: 4

# Scenario
A DevOps engineer needs to maintain multiple AWS accounts that belong to different OUs in the organization. All resources, including IAM policies and S3 policies within an account, are deployed through CloudFormation. All templates and code are maintained in a CodeCommit repository.
Recently, some developers have not been able to access an S3 bucket from some accounts in the organization.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject*", "s3:PutObject*"],
      "Principal": {
        "AWS": "arn:aws:sts::*:assumed-role/developer-role/access-session"
      },
      "Resource": [
        "arn:aws:s3:::DOC-EXAMPLE-BUCKET",
        "arn:aws:s3:::DOC-EXAMPLE-BUCKET/*"
      ]
    }
  ]
}
```

# Question
What should the DevOps engineer do to resolve this access issue?

# Options
1. Modify the S3 bucket policy. Turn off the S3 Block Public Access setting on the S3 bucket. In the S3 policy, add the aws:SourceAccount condition. Add the AWS account IDs of all developers who are experiencing the issue.
2. Verify that no IAM permissions boundaries are denying developers access to the S3 bucket. Make the necessary changes to IAM permissions boundaries. Use a Config recorder in the individual developer accounts that are experiencing the issue to revert any changes that are blocking access. Commit the fix back into the CodeCommit repository. Invoke deployment through CloudFormation to apply the changes.
3. Configure an SCP that stops anyone from modifying IAM resources in developer OUs. In the S3 policy, add the aws:SourceAccount condition. Add the AWS account IDs of all developers who are experiencing the issue. Commit the fix back into the CodeCommit repository. Invoke deployment through CloudFormation to apply the changes.
4. Ensure that no SCP is blocking access for developers to the S3 bucket. Ensure that no IAM policy permissions boundaries are denying access to developer IAM users. Make the necessary changes to the SCP and IAM policy permissions boundaries in the CodeCommit repository. Invoke deployment through CloudFormation to apply the changes.

# Explanation
The bucket policy already allows the developer role.

When some accounts in an Organization suddenly lose access despite a valid resource policy, the usual culprits are the two org-level guardrails that can override an Allow with an implicit or explicit Deny:

- SCPs attached to OUs
- IAM permissions boundaries on the developer principals

Since everything is managed by CloudFormation, any fix must also be made in the infrastructure code.

4 is the only option that correctly diagnoses SCP + permissions-boundary denies and applies the fix through the existing IaC pipeline.

1. Turning off S3 Block Public Access and making the bucket public is wrong and dangerous; access is via an assumed IAM role, not anonymous. aws:SourceAccount doesn't fix an SCP/boundary deny.
2. AWS Config is a recorder/compliance tool; it does not "revert changes to restore access." Also it bypasses the CodeCommit/CloudFormation deployment model.
3. Adding an SCP that stops modifying IAM does nothing to restore lost S3 access, and aws:SourceAccount is the wrong condition here.
