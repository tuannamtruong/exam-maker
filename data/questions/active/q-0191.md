correct: 1,4

# Scenario
A company groups its AWS accounts in OUs in an organization in Organizations. The company has deployed a set of API Gateway APIs in one of the Organizations accounts. The APIs are bound to the account's VPC and have no existing authentication mechanism. Only principals in a specific OU can have permissions to invoke the APIs.

The company also updates the API Gateway resource policies to deny invocations that do not come through the interface VPC endpoint. After the updates, the following error message appears during attempts to use the interface VPC endpoint URL to invoke an API: "User: anonymous is not authorized."

# Question
Which combination of steps should the company take to fix this? (Select TWO.)

# Options
1. Enable IAM authentication on all API methods by setting IAM as the authorization method.
2. Create a token-based Lambda authorizer that passes the caller's identity in a bearer token.
3. Create a request parameter-based Lambda authorizer that passes the caller's identity in a combination of headers, query string parameters, stage variables, and $context variables.
4. Verify the identity of the requester by using Signature Version 4 to sign client requests by using AWS credentials.

# Explanation
If the request is anonymous, there is no IAM principal, there is no Organization membership, and aws:PrincipalOrgPaths cannot be evaluated.

Without IAM authorization, API Gateway treats the caller as anonymous. Once IAM authorization is enabled, clients must authenticate themselves. For API Gateway, this means signing every request with Signature Version 4 (SigV4) using AWS credentials.

2. A token-based Lambda authorizer uses custom bearer tokens. It does not provide an IAM principal for evaluating aws:PrincipalOrgPaths, so it does not satisfy the VPC endpoint policy.
3. A request parameter-based Lambda authorizer likewise uses custom identity sources rather than an IAM principal. aws:PrincipalOrgPaths cannot be evaluated, so it does not satisfy the VPC endpoint policy.
