# Scenario
The goal is to process the logs before delivering the processed logs to the S3 bucket.

# Question
How?

# Options
1. Develop a Lambda function to transform the data and save a new object in the existing S3 bucket. Set up an S3 trigger on this bucket to activate the Lambda function, specifying all object creation events as the trigger type. Ensure that recursive invocation is accounted for.
2. Use S3 Event Notifications to trigger a Glue job. Configure the job to transform the logs and write the processed data back to the existing S3 bucket. Ensure the Glue job is set to handle structured and unstructured log formats.
3. Set up a Data Firehose delivery stream with a Lambda transformer. Designate the current S3 bucket as the destination. Modify the Network Firewall logging to use Data Firehose instead of S3.
4. Set up SQS to queue the logs before processing. Use a Lambda function triggered by SQS to transform the logs and save the results to the existing S3 bucket. This setup provides a buffer to handle spikes in log volume efficiently.

# Explanation
Firehose allows you to capture, transform, and send data in near real-time.

1. Setting up a Lambda function with an S3 trigger introduces the risk of recursive invocation, with the Lambda function creating new events by writing transformed objects back to the bucket. Additionally, this approach processes logs after they are written to S3, not before, failing to meet the requirement.

2. Triggering a Glue job with S3 Event Notifications would simply process logs after they are already stored in the bucket, which violates the requirement to transform the logs before storage. Glue is suitable for batch transformations but not for real-time processing.

4. Using SQS with a Lambda function can only process logs but does not natively handle the direct integration and delivery pipeline to S3 like Data Firehose. This solution adds operational complexity, requiring custom logic for retries and scaling, which Data Firehose inherently provides.
