# Scenario
A company needs to accelerate the performance of its AI-powered medical diagnostic application by running its machine learning workloads on the edge of telecommunication carriers' 5G networks. The application must be deployed to a Kubernetes cluster and have RBAC access to IAM users and roles for cluster authentication.

# Question
Which solution ensures single-digit millisecond latency for the application?

# Options
1. Host the application to an EKS cluster and run the Kubernetes pods on AWS Fargate. Create node groups in AWS Wavelength Zones for the EKS cluster. Add the EKS pod execution IAM role (EKSFargatePodExecutionRole) to your cluster and ensure that the Fargate profile has the same IAM role as your EC2 node groups.
2. Host the application to an EKS cluster. Set up node groups in AWS Wavelength Zones for the EKS cluster. Attach the EKS connector agent role (ECSConnectorAgentRole) to your cluster and use AWS Control Tower for RBAC access.
3. Launch the application to an EKS cluster. Create node groups in AWS Wavelength Zones for the EKS cluster via the Wavelength service. Apply the AWS authenticator configuration map (aws-auth ConfigMap) to your cluster.
4. Launch the application to an EKS cluster. Configure the VPC CNI plugin for Kubernetes to manage pod networking in AWS Wavelength Zones. Install the AWS IAM Authenticator for Kubernetes (aws-iam-authenticator) to your cluster.

# Explanation
AWS Wavelength combines the high bandwidth and ultralow latency of 5G networks with AWS compute and storage services so that developers can innovate and build a new class of applications.

EKS uses IAM to provide authentication to your Kubernetes cluster, but it still relies on native Kubernetes RBAC for authorization. This means that IAM is only used for the authentication of valid IAM entities. All permissions for interacting with your EKS cluster’s Kubernetes API are managed through the native Kubernetes RBAC system.

Access to your cluster using IAM entities is enabled by the AWS IAM Authenticator for Kubernetes, which runs on the EKS control plane. The authenticator gets its configuration information from the aws-auth ConfigMap (AWS authenticator configuration map).

The aws-auth ConfigMap is automatically created and applied to your cluster when you create a managed node group or when you create a node group using eksctl. It is initially created to allow nodes to join your cluster, but you also use this ConfigMap to add RBAC access to IAM users and roles.

1. Although this solution is possible, the security configuration of the EKS control plane is wrong. You have to ensure that the Fargate profile has a different IAM role as your EC2 node groups and not the other way around.
2. An EKS connector agent is only used to connect your externally hosted Kubernetes clusters and to allow them to be viewed in your AWS Management Console. The AWS Control Tower doesn’t provide RBAC access too to your EKS cluster. This service is commonly used for setting up a secure multi-account AWS environment and not for providing cluster authentication using IAM users and roles.
4. The VPC CNI plugin is primarily for enabling pods to get IP addresses from the VPC and is just the default networking model for EKS. It is not explicitly tied to Wavelength deployment. Similarly, installing the IAM Authenticator manually is unnecessary since EKS already integrates IAM authentication by default.  xtra steps that are irrelevant in this context.
