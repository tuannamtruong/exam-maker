# Scenario
A company stores application logs in CloudWatch Logs.  The logs contain employee IDs that follow this pattern:  Emp-123456  Engineers can view the logs but must not see employee IDs.  Only authorized personnel should be able to reveal (unmask) the IDs.  
Only future log entries need to be masked.

# Question
least operational effort?

# Options
1.	Create a new data protection policy on the log group. Add an Emp-\d{6} custom data identifier configuration. Create an IAM policy that has a Deny action for logs:Unmask. Attach the policy to the engineering accounts. 
2.	Create a new data protection policy on the log group. Add managed data identifiers for the personal data category. Create an IAM policy that has a Deny action for "NotAction":"logs:Unmask". Attach the policy to the engineering accounts. 
3.	Create a Lambda function to parse log entries, remove employee IDs, and write the results to another log group. Create a subscription filter to invoke the Lambda. 
4.	Stream logs to S3 through Data Firehose, remove engineers' logs:* permissions, and use Macie with a custom identifier.

# Explanation
CloudWatch Logs supports Data Protection Policies.
These policies can:
- inspect >new< incoming log events
- detect sensitive data using regex
- automatically mask matching values

2. managed data identifiers: email, phone, SSNs... --> A custom data identifier is required.
"NotAction":"logs:Unmask" is nonsensical here.

3. This would work technically but requires much more effort.
4. Macie does not mask CloudWatch Logs.
