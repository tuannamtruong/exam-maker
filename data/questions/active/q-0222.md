# Scenario
An organization has a hybrid infrastructure across various AWS regions and its own data centers, which includes EC2 instances, IoT Greengrass devices, and on-premises servers. A cloud consultant is tasked with streamlining resource management and ensuring devices are secured with the latest patches. The goal is to automate patch management and have regular scheduled maintenance to keep software current.

The organization has ensured that Systems Manager is available in all AWS regions hosting their resources and in the region nearest to their data centers.

# Question
What are the steps to meet this operational management need? (Select TWO.)

# Options
1. Set up an IAM instance profile for a custom IAM role with Systems Manager as a Trusted Entity. Attach this instance profile to all EC2 instances that will be managed. Use Systems Manager Patch Manager to schedule patching of the EC2 instances.
2. Generate an activation code and ID in Systems Manager or via the Command Line Interface (CLI). Set up an IAM service role with appropriate permissions and policies to allow Systems Manager to interact with the IoT Greengrass devices and on-premises servers. Assign a token exchange role to Greengrass core devices. Initiate token exchange and establish a secure connection by installing the Systems Manager Agent (SSM Agent) on the on-premises servers and IoT Greengrass devices. Use Systems Manager Patch Manager to schedule patching of the on-premises servers and the IoT Greengrass devices.
3. Create an IAM policy defining permission for Systems Manager Session Manager. Attach the policy to an IAM role which includes ssm.amazonaws.com as a trusted entity. Associate the IAM role to the IoT Greengrass devices and on-premises servers to allow Session Manager to push scheduled patches to the devices.
4. Create a custom IAM policy defining permissions to Systems Manager Run Command. Attach the policy to an IAM role which includes ssm.amazonaws.com as a trusted entity. Associate the IAM role to the EC2 instances. Use Systems Manager Run Command to use the IAM role to run scheduled patching commands to the EC2 instances.
5. Create a custom state configuration with Systems Manager State Manager. Associate the state configuration with the EC2 instances, IoT devices, and the on-premises servers. State Manager will continuously monitor the state of the resources and apply the latest patches when available.

# Explanation
For EC2 instances within AWS, an instance profile needs to be specified during the instance launch. The instance profile will have the attached IAM role that allows AWS System Manager permissions to manage the instances. For IoT Greengrass devices and on-premises servers, an IAM service role that is configured with a trusted entity resource has to be set up. The role can be used by Greengrass devices or on-premises servers for communication with AWS services such as AWS Systems Manager. In addition to the service role that authorizes service-level access, a token exchange role should be assigned to Greengrass core devices. The token exchange role is a separate IAM role that controls how Greengrass components can access AWS services.

3. Systems Manager Session Manager is primarily used for interactive shell access to EC2 instances and not for handling patch management. Although it can be used to run commands on managed instances, it’s not the recommended tool for scheduling regular patching tasks.

4. While Systems Manager Run Command can be used to execute commands or scripts at scale, it does not have a scheduling capability and would require the setup of additional AWS services like EventBridge. It is also not the recommended tool for scheduling regular patching tasks.
The trust policy is wrong for the attachment described. The option says the role trusts ssm.amazonaws.com, then associates it with EC2 instances. A role attached to an instance must trust ec2.amazonaws.com
The permissions point the wrong direction. The instance role doesn't need permission to call Run Command. Run Command is invoked by you (console/CLI/API) against the instance; the instance side only needs to reach the SSM endpoints — ssm:* messaging plus ssmmessages and ec2messages, which is what AmazonSSMManagedInstanceCore grants. Giving an instance ssm:SendCommand doesn't let it be patched; it lets that instance issue commands to other instances. Backwards, and a privilege-escalation footgun.

5. State Manager is mainly used to improve the management and governance of AWS resources and reduce configuration drift. It does not provide capabilities to schedule and automate patch management.
