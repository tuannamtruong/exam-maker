# Scenario
A tech startup has recently migrated their microservices architecture to AWS. They are utilizing Elastic Kubernetes Service (EKS) to orchestrate their containerized applications. For monitoring, they have chosen Managed Service for Prometheus. The applications are running in an EKS cluster in the startup’s AWS account. The startup’s engineering team wants to be notified of any critical alerts related to their applications. They have an existing Simple Notification Service (SNS) topic set up for notifications, which is in the same AWS account as the EKS cluster.

# Question
What sequence of actions should the engineering team take to achieve this requirement? (Select THREE.)

# Options
1. Configure the Managed Service for Prometheus to use the alert manager configuration and set up an alerting rule for critical alerts
2. Update the SNS topic’s access policy to grant the Managed Service for Prometheus service the sns:Publish and sns:GetTopicAttributes permissions.
3. Configure the alert manager to send notifications to the SNS topic when the alerting rule is triggered.
4. Use the OpenID Connect (OIDC) to authenticate the SNS topic.
5. Configure the EKS cluster to send notifications to the SNS topic when the alerting rule is triggered.
6. Set up an IAM role with the sns:Publish and sns:GetTopicAttributes permissions and associate it with the EKS cluster.

# Explanation
Managed Service for Prometheus has a built-in alert manager, so the alerting pipeline lives entirely inside the service.
The alert manager configuration and alerting rules are essential components of this service, which allow it to generate alerts based on specific conditions. -> 1

The Amazon Managed Service for Prometheus needs these permissions to publish notifications to the SNS topic when an alert is triggered. By updating the access policy of the SNS topic to grant these permissions, you allow AMP to publish notifications to the SNS topic. -> 2

The alert manager is responsible for dispatching alerts generated by the Amazon Managed Service for Prometheus. By configuring it to send notifications to the Amazon SNS topic, the engineering team can be notified of any critical alerts related to their applications. -> 3

4. OIDC is used for IAM roles for service accounts (IRSA). Authentication between the services via OIDC is not required for Prometheus to send notifications to SNS.

5. EKS cluster is not responsible for generating or sending alerts. The alerting rules and the routing configuration live in the Managed Service for Prometheus workspace, and its alert manager is what publishes to the topic.

6. Access for Managed Service for Prometheus is granted through the SNS topic’s resource policy to the service principal. EKS cluster does not need to publish messages to the Amazon SNS topic.
